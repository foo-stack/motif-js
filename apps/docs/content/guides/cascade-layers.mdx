# Cascade layers

<Lede>
  By default motif's base style props resolve to inline styles, which beat any class your existing
  stylesheet contributes. Set `cssLayer` and motif emits everything into a CSS cascade layer
  instead, so you decide which side wins.
</Lede>

<ArticleMeta />

## When you need this

You need it when motif has to coexist with a stylesheet you already ship — the usual case being an
incremental migration off Tailwind.

Without a layer, a base style prop lands in `style={...}`, specificity `1,0,0,0`. Anything your
stylesheet contributes is a class, `0,1,0`. So motif wins, whatever the authoring order:

<CodeBlock lang="tsx" code={`// The caller's class loses. In a tailwind-merge codebase this is backwards —
// there, the caller's class is expected to win.
<Button className="bg-blue-600">Save</Button>`} />

Source order can't fix it either. Rules motif injects at runtime go into `document.head` *after*
your bundled stylesheet, and the order between two injected chunks isn't stable under code
splitting.

Cascade layers settle precedence independently of both specificity and source order, which is
exactly the axis in question.

## Turn it on

Two places, the same name — the same shape as [configuring
breakpoints](./configuring-breakpoints.mdx).

### The provider

<CodeBlock lang="tsx" code={`<ThemeProvider themes={themes} active="dark" cssLayer="motif">
  <App />
</ThemeProvider>`} />

### The compiler

If you use the compiler plugin, pass the same name, or compiled and runtime rules hash to different
class names and stop deduplicating:

<CodeBlock lang="ts" code={`// vite.config.ts
import motif from '@usemotif/compiler-web';

export default {
  plugins: [motif.vite({ cssLayer: 'motif' })],
};`} />

<Callout variant="warning">
  The layer name is part of the generated class name. A provider on `"motif"` and a compiler on
  `"motif-styles"` will emit two classes for one set of declarations.
</Callout>

### Declare the order yourself

Motif deliberately does **not** emit an `@layer` order statement. Layer order is decided by first
occurrence, so emitting one would race your stylesheet and make precedence depend on DOM insertion
timing — the non-determinism this feature exists to remove.

Declare it once, in a stylesheet that loads before motif:

<CodeBlock lang="css" code={`/* app.css - earlier layers lose */
@layer motif, app;`} />

Now your own CSS wins while you migrate. Flip the order when you're done:

<CodeBlock lang="css" code={`@layer app, motif;`} />

Unlayered CSS always beats layered CSS, so any stylesheet that declares no layer at all already
wins against a layered motif.

<Callout variant="warning" title="This only works if nothing declared layers first">
  A layer statement can position layers that do not exist yet, but it cannot **reorder** layers
  something else already declared. If a framework stylesheet loads before yours and declares its
  own layers, your statement appends to that order instead of replacing it. That is exactly what
  happens with Tailwind, below.
</Callout>

## With Tailwind v4

`@import "tailwindcss"` is not just a stylesheet. It emits its own order statement first:

<CodeBlock lang="css" code={`@layer theme, base, components, utilities;`} />

That one line drives both of the ways this goes wrong.

### Put the statement before the import

Written after the import, `@layer motif, app;` cannot move anything. `motif` and `app` are names
Tailwind never declared, so they are appended, and the real order becomes:

<CodeBlock lang="css" code={`theme, base, components, utilities, motif, app`} />

motif now outranks every Tailwind layer, which is the opposite of what you wanted. It is also
ordering motif against a layer named `app` that Tailwind puts nothing in.

### Do not put motif first

The obvious correction is to move motif to the front. Tailwind then wins, and that includes
preflight:

<CodeBlock lang="css" code={`/* Wrong: motif sits below Tailwind's base layer. */
@layer motif, theme, base, components, utilities;`} />

Preflight's universal reset sets `margin: 0` and `padding: 0` on every element, and those are the
only two properties in it that motif's base style props also set. So padding and margin silently
stop working while colour, background, and everything else keep going. It reads like a motif bug
rather than a cascade one.

### The ordering that works

Slot motif **between `base` and `components`**, in a stylesheet that loads before Tailwind:

{/* docs-check: canonical-layer-order. `yarn docs:check` reads the statement in
    the next code block and fails if it stops matching what motif documents.
    The guide shows broken orderings too, so the canonical one is marked. */}

<CodeBlock lang="css" code={`/* app.css */
@layer theme, base, motif, components, utilities;
@import "tailwindcss";`} />

Preflight can no longer clobber motif, and a Tailwind utility still overrides motif, which is what
an incremental migration wants:

<CodeBlock lang="tsx" code={`{/* padding comes from the utility, margin from motif */}
<Box m="$2" p="$3" className="p-8" />`} />

<Callout variant="info" title="Yes, @layer really can precede @import">
  `@import` has to come before other rules, with two exceptions: `@charset` and `@layer`
  statements. Putting the order statement above the import is legal, and here it is required.
</Callout>

This repo pins all three orderings in `apps/docs/tests/cascade`, so the guide and the behaviour
cannot drift apart.

## What changes when you set it

**Base style props become a class.** Inline styles cannot belong to a layer at all, so motif emits
them as a class instead — otherwise the layer would have no effect on exactly the styles you set it
up to control.

Everything else about them is unchanged: the same declarations, the same values, the same order
relative to responsive and pseudo rules. In an app with no competing stylesheet the rendered result
is identical.

**Everything motif emits is wrapped.** The theme variable block, the runtime block (`@font-face`,
resets, the reduced-motion guard), responsive and container at-rules, pseudo-state rules, and
`@keyframes`.

**One layer, not one per tier.** Inside a layer, specificity and source order still apply normally,
so a single layer preserves every base → responsive → pseudo relationship motif already relies on.
Splitting those across sub-layers would make specificity irrelevant *between* them and break the
overrides.

<Callout variant="info">
  Imperative writes still win. Enter/exit animations and motion values write to the element's
  `style` directly, which stays outside the layer — an animation in flight should beat a static
  rule.
</Callout>

## Testing with jsdom

jsdom does not implement cascade layers. It parses an `@layer` statement, but it drops the
**contents** of every `@layer` block, so the rules inside never apply.

That means a component test running in jsdom with `cssLayer` set sees none of motif's styles at
all. It is not a motif bug and there is nothing to configure around it. Assert on emitted CSS text
or on class names in unit tests, and keep any assertion about layer precedence in a real browser.

## On native

`cssLayer` is accepted and ignored by the React Native provider. There is no cascade on native —
styles resolve to a flat `StyleSheet` object — so the prop exists only so a shared cross-platform
provider typechecks.
