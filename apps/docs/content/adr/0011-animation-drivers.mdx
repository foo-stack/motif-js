# Animation drivers

<Lede>
  Motion is the one place where web and native genuinely diverge — a CSS transition and a
  Reanimated worklet have nothing in common at runtime. Rather than expose that seam, motif puts a
  driver behind every animated primitive: one selection API, a conservative default, and an opt-in
  driver that reaches further on each platform.
</Lede>

<ArticleMeta />

## Status

Accepted.

## Context

A motif primitive declares motion the same way on both platforms — `enterStyle`, `exitStyle`,
`transition`, motion values. How that declaration becomes movement is platform-specific and not
small: on web it is a CSS transition (and, increasingly, the Web Animations API); on native it is
React Native's `Animated`, or Reanimated worklets on the UI thread. These have different threading
models, different interruption semantics, and different performance envelopes.

Native already had a driver abstraction: `getMotionDriver()` returns the active driver, the default
`animatedDriver` uses React Native's `Animated`, and `reanimatedDriver` (opt-in, from a separate
entry) moves the work to the UI thread. The web side had no such seam — entry animations were a
hardcoded overlay-plus-CSS-transition path, motion values were direct `element.style` writes, and
there was no way to ask for anything else.

That asymmetry is a problem the moment you want web animation to reach further — off-main-thread
playback, interruptible enter/exit, springs that don't run a JS rAF loop on the main thread. With
no abstraction, the only way to add those is to change the one hardcoded path for everyone.

## Decision

Web gets the same driver model as native: a single active driver, selected once at startup, behind
every animated primitive.

<CodeBlock lang="ts" code={`import { registerMotionDriver, waapiDriver } from '@usemotif/react';

registerMotionDriver(waapiDriver); // default is cssDriver`} />

- **`cssDriver`** (default) — the behavior motif has always had. Entry renders the `from` overlay for
  one client frame, then drops it so the declared CSS `transition` interpolates to rest. SSR and the
  first client render show the resting style; no FOUC, no hydration mismatch. Output is byte-for-byte
  what it was before the driver layer existed.
- **`waapiDriver`** (opt-in) — runs the entry off the main thread with
  `element.animate([from, {}], { fill: 'backwards' })`, with imperative control (cancel on unmount)
  the CSS path can't offer. It lives in its own side-effect-free module, so it tree-shakes out of any
  bundle that never imports it.

Selection mirrors native exactly: `registerMotionDriver(driver)` sets the active driver,
`registerMotionDriver(null)` reverts to the default, `getMotionDriver()` reads it. The same function
names are exported from `@usemotif/react` and `@usemotif/react-native`, so the wiring reads
identically on both platforms.

This is deliberately the **same shape as the [compiler's optimization
levels](/adr/0010-optimization-levels)**: a conservative default that never surprises, and an
explicit, auditable opt-in for teams that want more. Turning motif on never changes how your
animations behave; reaching for an off-thread driver is a separate, named choice.

### Asymmetric enter and exit

The motion model also carries timing per phase. `transition` times the enter (and ordinary prop
changes); a `transition` placed _inside_ `exitStyle` overrides it for the exiting phase only:

<CodeBlock lang="tsx" code={`<Box
  transition={{ property: 'opacity', duration: '$durations.2' }}        // enter: quick
  enterStyle={{ opacity: 0 }}
  exitStyle={{ opacity: 0, transition: { property: 'opacity', duration: '$durations.5' } }} // exit: slow
/>`} />

This is pure CSS — the exit transition is emitted into the `[data-motif-state="exiting"]` rule and
the base `transition` is lifted from inline to a class so the exit rule wins the cascade — so it
behaves identically no matter which driver is active. `enterStyle` does not take its own
`transition`: enter animates on the base `transition`, and a silent-no-op field would be worse than
its absence, so the type omits it.

## Consequences

- A team can move web animation off the main thread by registering one driver, with no change to any
  component's markup — exactly the native ergonomics.
- The default is untouched. Adopting motif, or upgrading, never changes animation behavior; the
  conservative `cssDriver` is what runs until someone opts out of it.
- The boundary is honest about what's done. The `waapiDriver` today owns the **entry** animation.
  Exit on web is still the CSS-cascade path (a parent boundary sets `[data-motif-state="exiting"]`
  and motif's `exitStyle` rule animates the element out), which is renderer-agnostic and lives in the
  headless layer. Letting a driver own the exit imperatively — off-thread, interruptible — needs a
  web presence-context mirroring native's, and is a later step. Asymmetric exit timing already works
  under either driver because it is CSS.
- The model can grow — more driver capabilities (off-thread springs, drag backing), broader exit
  ownership — and every addition stays behind the same one-driver-at-a-time selection, held to the
  same "default never changes" bar.
